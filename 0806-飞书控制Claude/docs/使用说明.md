# 飞书 <-> Claude Code 桥接服务

手机飞书私聊消息 → 这台 Mac 上的 Claude Code（无头模式，持续会话）→ 结果回复到飞书。

## 工作原理

1. `lib/bridge.sh` 通过 `lark-cli event consume im.message.receive_v1` 订阅飞书机器人收到的消息事件（WebSocket 长连接，无需公网端口）。
2. 每条消息交给 `lib/handle_message.sh` 处理：
   - 鉴权：只有 `config/bridge.env` 里 `ALLOWED_SENDER_OPEN_ID` 指定的账号发的消息才会被执行，且只处理私聊（p2p）文本消息。
   - 调用 `claude -p "<消息内容>" --dangerously-skip-permissions --output-format json`，并按 `chat_id` 维护会话：同一个聊天窗口的多条消息会 `--resume` 同一个 Claude 会话，可以连续追问。
   - 把 Claude 的回复通过 `lark-cli im +messages-send` 发回原聊天窗口。
3. 所有事件、Claude 原始输出、飞书发送结果分别记录在 `logs/bridge.log`、`logs/claude.log`、`logs/lark-send.log`。

## 日常管理命令

都在 `scripts/` 目录下，不要绕开脚本直接敲 `lark-cli` / `claude` 命令：

| 命令 | 作用 |
|---|---|
| `./scripts/status.sh` | 查看服务是否在跑、当前会话列表、最近日志 |
| `./scripts/start.sh` | 前台启动（调试用，Ctrl-C 停止） |
| `./scripts/stop.sh` | 停止服务（前台或常驻均可） |
| `./scripts/install-daemon.sh` | 注册为 LaunchAgent，开机/登录自启常驻 |
| `./scripts/uninstall-daemon.sh` | 卸载 LaunchAgent，不再自启 |

常驻服务日志：

```bash
tail -f logs/bridge.log      # 收发消息主日志
tail -f logs/claude.log      # Claude Code 原始 stderr
tail -f logs/lark-send.log   # 飞书发送接口原始返回
```

## 会话管理

- 每个飞书聊天窗口（`chat_id`）对应一个独立的 Claude 会话，存在 `var/sessions/<chat_id>.session_id`。
- 想让某个聊天窗口"重新开始"（清空上下文），删掉对应的 session 文件即可：
  ```bash
  rm var/sessions/<chat_id>.session_id
  ```
- Claude 的默认工作目录是 `CLAUDE_WORK_DIR`（当前设置为 `cy26-projects` 根目录），可以直接在飞书消息里让它 `cd` 到具体项目。

## 安全边界（务必了解）

- 这条链路对 Claude Code 使用了 `--dangerously-skip-permissions`：**只要是 `ALLOWED_SENDER_OPEN_ID` 这个账号发的消息，都会被无确认地执行**，包括文件读写、执行 shell 命令等。这意味着任何能拿到你手机/飞书账号的人，等于拿到了这台 Mac 的操作权限。
- 唯一的防线是发送者白名单（`sender_id` 校验），没有其他确认步骤。如果需要更强的安全性，后续可以考虑：
  - 改用 `--permission-mode` 而非全跳过，牺牲一些远程便利性换取危险操作的二次确认；
  - 给消息加一个约定的口令/前缀校验；
  - 限制 `CLAUDE_WORK_DIR` 或用 `--add-dir` 收紧可访问目录。
- 群聊消息、非白名单账号的消息会被直接忽略（不回复，避免暴露"这个机器人背后接了 Claude Code"这件事）。

## 已知限制

- Claude 的单次回复如果非常长（比如大段代码），飞书文本消息可能显示不全或截断，目前没做分片/转 Markdown 文件处理。
- 没有做消息去重；正常情况下 `lark-cli` 的事件推送不会重复，但极端网络情况下理论上可能重复触发一次执行。
